# ADR 0004: векторный поиск отложен

- Статус: принято
- Дата: 2026-10-22
- Владелец: A (домен/данные/поиск)

## Контекст

`PLAN.md` и `AGENTS.md` описывают `embedding vector(1024)` и HNSW-индекс
`events_embedding_idx`, включаемые флагом `ENABLE_VECTOR_SEARCH`. В окружении
разработки/демо используется PostgreSQL 18, в котором доступны только
`btree_gist` и `pg_trgm`; расширение `pgvector` не установлено:

```sql
SELECT name FROM pg_available_extensions WHERE name = 'vector'; -- 0 rows
```

Установка системного пакета `postgresql-18-pgvector` требует прав, которых у
участника A нет. Тесты и миграции должны применяться в текущем окружении,
поэтому делать миграцию, падающую без `pgvector`, нельзя.

## Решение

1. Ядро поиска работает на PostgreSQL FTS (`russian`) + `pg_trgm`:
   `ts_rank_cd` и `similarity`, без позиционной эвристики.
2. `events.embedding` остаётся `JSONB`-заглушкой. Контракт API от этого не
   меняется: поле не является частью DTO.
3. `events_embedding_idx` и HNSW не создаются в миграции `0002`.
4. `ENABLE_VECTOR_SEARCH` остаётся `false`; `embeddings_provider=off`.
5. В README и `project/docs/api/README.md` явно указано ограничение.

## Последствия

- Обязательные сценарии (создание, список, поиск) работают без pgvector.
- Векторный поиск и Recall@5 по эмбеддингам в этом окружении не проверяются.
- При появлении `pgvector` нужна отдельная миграция:
  `CREATE EXTENSION vector`, преобразование `embedding` в `vector(1024)`,
  HNSW-индекс и включение флага. Это изменение схемы и контракта — только
  после согласования с B и обновления `PLAN.md`/ADR.

## Альтернативы

- Установить `pgvector` в систему — отклонено: нет прав и это меняет
  окружение за пределами зоны A.
- Хранить эмбеддинги в памяти/файле — отклонено: не переживает перезапуск и
  не соответствует PostgreSQL-модели.
- Удалить `embedding` — отклонено: поле понадобится при включении флага.
